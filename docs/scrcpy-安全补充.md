# 补充：scrcpy 调试后的黑屏风险与恢复（2026-11-09 实测）

> 这一节建议加到《使用 scrcpy 远程查看电视画面》指南的开头或结尾，内容可直接复制粘贴。

## ⚠️ 已确认的事故

今天调试 scrcpy 时做了两件事：

1. 反复触发默认硬件编码器 `OMX.MS.AVC.Encoder` 崩溃（这台海信 VIDAA_TV / MTK9652 的硬编必崩）；
2. 把软件编码的分辨率、帧率调高做压测。

之后电视出现：**所有视频 App 都播不了** —— 自研小剧场卡在黑屏 + 黄色加载圈（播放器一直处于缓冲），优酷「有声音、没画面」。

排查后排除：NAS、片单 `tv.json`、SMB 账号密码、视频文件本身、电视网络、App 的 15 秒清单轮询。
日志特征为 `setPortMode ... failed -1010`、`allocateNativeHandle ... BadPortIndex`，即视频输出端口协商失败。

**结论：MTK9652 上编码与解码共用同一套多媒体链路，编码器崩溃 / 高分辨率软编压测会把它卡死。
这不是 App 或 NAS 的问题，只有重启电视才能恢复。**

2026-11-09 20:45 通过 ADB 重启后复测：播放页连续 30 秒稳定、音频在播、硬解输出层正常、无「打开失败 / 自动重试 / 播放失败」，故障消失。

## 安全参数（不要再改）

```bash
scrcpy -s <电视IP>:5555 --no-audio --video-codec=h264 \
  --video-encoder=OMX.google.h264.encoder --max-size=960 --max-fps=15 -b 2M
```

- **不要提高 `--max-size` / `--max-fps`**：这台机软编性能弱，高分辨率会压垮共享视频链路。
- **不要用默认硬编，也不要反复启停重试**：`OMX.MS.AVC.Encoder` 必然崩，反复崩最容易留下残状态。
- 不要加 `--turn-screen-off`；Android 9 不支持 scrcpy 音频转发，必须 `--no-audio`。
- 不要把 5555 端口映射到公网（ADB 无认证）。

一键脚本 `tv-mirror.bat` 已内置上述参数，并写明警告与恢复提示。

## 编码崩溃 / 画面冻住之后怎么处理

1. 立刻停止 scrcpy（Ctrl+C 或 Alt+Q），**不要继续重试**。
2. **重启电视**：拔电源等 10 秒再插，或 `adb reboot`。重开 App、停后台进程都无效。
3. 开机后按一次 **HOME** 进入小剧场（VIDAA 不给第三方开机广播，这是固有限制）。
4. 先播一个视频确认出画面，再正常使用其它 App。
5. 若重启后仍黑屏，再考虑在电视图像设置里关 MEMC / HDR，或让播放器走软件解码回退。

## 黑屏时的自查顺序

| 检查 | 正常应该看到 |
|---|---|
| 播放日志 | `Video Start Playing`、硬解输出层 present；而不是一直 `STATE_BUFFERING` |
| 其它视频 App | 同样黑屏 → 系统解码链路问题；只有某一个 App 黑屏 → 查该 App |
| 音频 | 有声音没画面 = 音频解码独立正常，视频渲染链路卡住 |
| 最近一次开机时间 | 若事故后从未重启过，先重启再谈其它优化 |
| NAS / 片单 / 网络 | 用 SMB 单独读一次文件，能读到就与本次黑屏无关 |

## 一句话

**看画面用低分辨率软编即可，别拿这台电视做编码压测；一旦崩过，先重启电视再播任何视频。**
