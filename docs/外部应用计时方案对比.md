## 1. 问题有多严重

`Extras.addWatchMs()` 全项目只有两个调用点，都在 `PlayerActivity`（275、353 行）。`KidApp` 的 1 秒 tick 只做锁屏判定，不从外部应用计时。

结果是：家长允许的「优酷」入口给了 30 分钟放行窗口（`AppsConfig.maxMinutes`），这 30 分钟**一秒都不进 `dailyLimitMinutes`**。孩子只要发现「从应用入口看更划算」，整套限额就废了。这不是体验问题，是规则漏洞。

> 附：`PACKAGE_USAGE_STATS` 权限已在 `AndroidManifest.xml` 第 6 行声明（`tools:ignore="ProtectedPermissions"`），`AppGuard.foregroundPackage()` 的读取逻辑也写好了。**缺的只是一次 `appops` 授权**，代码不需要从零写。

## 2. 判定口径（先定标准，再选方案）

| 项 | 要求 | 理由 |
|---|---|---|
| 计时区间 | 从进入外部应用起，到离开（Home / 切到别的应用 / 回小剧场）止 | 只算真正在看的时段 |
| 精度 | 单次误差 ≤ 60 秒，一天累计误差 ≤ 3 分钟 | 孩子不会因为误差几十秒就少看一集 |
| 失效方向 | **宁可多扣，不可少扣** | 少扣 = 规则被绕过；多扣家长可以手动退还 |
| 时钟 | 不能用墙上时间（见 OPT-02） | 否则改时间又能绕 |
| 性能 | 不能常驻高耗电、不能碰 SMB 主连接 | MTK9652 + 2.5 GB，历史上有挂死事故 |
| 可回滚 | 出问题改 `tv.json` 的 `features.extWatchMs=false` | 见 OPT-00 |

## 3. 五个候选方案

| 方案 | 能拿到包名 | Android 9 可用 | 权限门槛 | 精度 | 失效行为 | 开发量 |
|---|---|---|---|---|---|---|
| **A. UsageStats 事件流** | 是 | 是（API 22+） | 需 `appops GET_USAGE_STATS` | 秒级 | 拿不到 → 返回 null | 1.5 人日 |
| **B. 无障碍服务** | 是（窗口级） | 是 | 需在设置里手动开无障碍 | 秒级，最准 | 服务被杀 → 漏记 | 3 人日 |
| **C. 进入即预扣** | 不需要 | 是 | 无 | 保守估计（多扣） | 永不失效 | 0.5 人日 |
| **D. VPN 流量法** | 否（只能看流量） | 是 | 需用户授权 VPN | 差 | 劫持全部流量，风险高 | 3 人日 |
| **E. ActivityManager** | 否 | 否（Android 5+ 只返回自己） | — | — | — | 不可行 |
| **F. 关掉外部入口** | 不需要 | 是 | 无 | 完美 | — | 0.2 人日 |

### A. UsageStats 事件流（推荐主路径）

- **原理**：`UsageStatsManager.queryEvents()` 拿 `MOVE_TO_FOREGROUND` / `MOVE_TO_BACKGROUND`，判断当前前台是不是家长允许的那个包；`SystemClock.elapsedRealtime()` 累计时长。
- **可靠性关键**：不要靠「事件里没有新事件就认为还在前台」，要走**双读**：
  1. **实时估算**：记住最后一次 `MOVE_TO_FOREGROUND(pkg)` 的时刻（`elapsedRealtime`），`now - 那一刻` 就是已看时长，每秒刷新，用于倒计时和提示；
  2. **结算校准**：`queryUsageStats(INTERVAL_DAILY)` 取该包的 `totalTimeInForeground` 累计值增量。累计值在部分 ROM 上是「应用退到后台才刷」，所以它能纠正实时估算的偏差，但不适合做秒级显示。
  3. 两者相差 > 20% 时以系统累计值为准，并记一条日志。
- **坑**：
  - 有些 ROM 把 usage 事件延迟 5–30 秒落地，所以「孩子刚打开就退出」可能漏记 —— 用 C 的预扣兜第一次。
  - 海信可能把「使用情况访问」入口藏在设置里，遥控器找不到 → 用 `adb appops` 一次性授权（见第 5 节）。
  - 万一固件裁剪了 `UsageStatsManager`，`queryEvents` 返回空 → 自动降级到 C，不能崩。

### B. 无障碍服务（备选，不推荐首发）

- **原理**：`AccessibilityService` 监听 `TYPE_WINDOW_STATE_CHANGED`，能拿到窗口所属包名，精度最高，也不依赖 usage stats。
- **为什么不首选**：
  1. 需要在电视设置里手动开无障碍，海信这台的入口位置不确定，遥控器操作成本高；
  2. 常驻服务在 2.5 GB 内存的中端芯片上被系统回收的概率不低，被回收就静默漏记；
  3. 无障碍权限在家庭场景里属于「过度授权」，一旦误配还可能干扰遥控器按键。
- **什么时候用**：如果实测 A 在这台机器上完全拿不到事件，再考虑把 B 作为第二路径。

### C. 进入即预扣（必须有，作为兜底）

- **原理**：`launchAllowedApp()` 里直接 `WatchClock.preCharge(maxMinutes)`，回来时按实际结算退还。
- **优点**：零权限、零依赖、**永远不会失效**，符合「宁可多扣」原则。
- **缺点**：只看了 2 分钟就退出，也会先扣 30 分钟。
- **缓解**：
  - 回到小剧场时提示「刚才看了 X 分钟」，X 来自 A 的实测值；有 A 就精确，没 A 就按预扣算；
  - 设置页加「刚才扣多了？退还 10 分钟」按钮，家长点一下即可（相当于 `grantTemp`）。

### D. VPN 流量法（否决）

判定「有没有视频流量」不等于判定「孩子在不在看」，而且 `VpnService` 会把 NAS 的 SMB 流量也接管进来——这台电视的所有播放都走 SMB，等于在核心链路上加一层代理。历史上 SMB 一出问题就是全站黑屏，不能在这里冒险。

### E. ActivityManager（不可行）

`getRunningTasks()` 从 Android 5 起只返回自己的任务，`getRunningAppProcesses()` 同样被限制。Android 9 上拿不到别的包，直接排除。

### F. 关掉外部应用入口（可作为家长的选项）

如果家里其实很少用优酷这类入口，最彻底的方案是 `apps.enabled=false`——规则上零漏洞，成本为零。建议保留这个选项，并在编辑器里写清楚「开启后该应用内的观看时间无法计入限额（除非启用精确计时）」。

## 4. 推荐：A + C 分层

```
进入外部应用
   ├─ 有 usage 授权 ──> A：实时估算 + 退出时系统值校准
   └─ 无授权 ────────> C：按 maxMinutes 预扣，回来退还/家长手动退

到点（GateKeeper 判定 open=false）
   └─ 守卫立刻拉回小剧场并锁屏（现有逻辑，不用改）
```

落地要点：

1. **状态机**放在 `WatchClock`（OPT-01）里，`owner = "ext:<pkg>"`，与播放页互斥，避免重复计数。
2. **每秒 tick** 由 `KidApp` 驱动（已有 1 秒节拍），不新建线程、不新建定时器。
3. **明细单独记**：`ext_yyyy-MM-dd` 记外部应用时长，`watch_yyyy-MM-dd` 仍记总时长。周报页（OPT-08）可以分开显示「小剧场内 / 外部应用」两条。
4. **界面提示**：外部应用里看不到我们的 UI，所以提示放在两处——放行剩 2 分钟时 `Toast`（若 ROM 允许后台 Toast），以及回到小剧场时的结算卡片。
5. **降级可见**：设置页显示当前模式「精确计时（已授权）」/「估算扣时（未授权）」，附一键授权说明，避免家长以为数字是准的。

授权只需要一次（重装 APK 也会保留，因为 `appops` 绑包名）：

```bash
adb connect 192.168.31.147:5555
adb shell appops set com.family.curated GET_USAGE_STATS allow
adb shell appops get com.family.curated GET_USAGE_STATS
```

## 6. 建议的落地顺序

> **状态更新**：架构已按本方案定稿，见 [ADR-01](ADR-外部应用计时.md)；[ROADMAP](ROADMAP.md) V1.2 已把 OPT-04 正式排到 Wave 2 之后、Wave 3 之前，不再是待定项。

1. 先做 OPT-01（`WatchClock`）与 OPT-02（时钟守卫）——这是所有计时的地基，与外部应用无关。
2. 电视开机时跑第 5 节 V1–V5，拿到结论（10 分钟的事）。
3. **V1–V5 全通过**：按 [ADR-01](ADR-外部应用计时.md) 做完整 A + C，1.5 人日。
4. **授权通过但拿不到事件流 / 授权失败**：只做 C（0.5 人日），设置页写明「估算模式」，并把「关掉应用入口」列为推荐配置。C 的预扣与退还无论哪条分支都必须实现。
5. 无论哪条路，`features.extWatchMs` 都默认 `false`，家长显式打开才生效。

## 7. 风险

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| 海信裁剪 usage 事件 | 中 | A 不可用 | 降级 C，规则仍闭合 |
| 预扣导致多扣，孩子被冤枉 | 中 | 家长不信任 | 结算卡片 + 手动退还 + 明细区分 |
| 后台 tick 被系统冻结 | 低 | 漏记 | 累计值校准 + 回小剧场时补结算 |
| 计时逻辑侵入播放页导致重复计数 | 中 | 双倍扣时 | owner 互斥 + 单测覆盖 |
